# 法析 Lexora 产品范围

## 产品定位

法析 Lexora 是面向个人用户的对话式 AI 法律案例分析助手，也是个人案件研究工作台。
它不是通用法律问答机器人或法律数据库搜索框，而是帮助用户把一件难以说明、材料分散的
法律问题，逐步整理成有依据、可核查、知道下一步该做什么的案件分析。

核心目标是帮助用户完成以下转变：

```text
“我遇到了一件事，但不知道什么重要”
    -> 关键事实与时间线
    -> 争议焦点与双方主张
    -> 证据支持、矛盾与缺口
    -> 已核验的法律依据
    -> 可执行的后续工作
```

## 目标用户

当前个人版首先服务于正在面对具体法律问题、但缺少案件整理方法的个人用户。用户可以不懂
法律术语，也不需要先把问题整理成专业表单。专业律师协作、组织权限和团队案件管理不属于
当前阶段。

## 核心体验

对话是入口，案件状态是记忆，RAG 是材料与法律依据检索引擎，案件分析是交付物。
Lexora v1 的推荐主链路不是“纯聊天问答”，也不是“先把所有信息问全再答”，而是
“结构化法律要素层 + RAG”：先把当前案件整理成可检查的法律要素，再判断信息是否已经足够
给出阶段性分析，并围绕这些要素做法规、司法解释和类案检索。

1. 用户直接用自然语言描述发生了什么。
2. 系统结合已有对话和材料识别已经明确的信息，不重复询问。
3. 即使事实尚不完整，也先给出有明确假设和边界的暂时结论，再追问最多两个会实质改变
   责任成立、法定区间、金额计算或下一步行动的问题。
4. 用户可以随时补充合同、聊天记录、通知、流水等材料。
5. Supervisor 按任务选择最少的专家和工具：简单法源问题直接研究，复杂案件按需整理事实，案件
   材料和已审核类案只在确有帮助时检索，不执行固定子 Agent 链路。
6. 用户继续补充或纠正后，后续分析沿用同一案件上下文并自然更新。

Case Analyst 的结构化理解必须逐项记录用户实际提出的问题，并为每项选择直接回答或条件分支回答。模型可以
识别当前措辞必然蕴含的信息来避免重复追问，但该结果只对本轮有效，不写入用户确认的案件事实。
追问候选必须说明它会改变责任成立、法定区间、金额计算还是下一步行动；应用层只放行仍未知的
高影响案件要素。案由和要素名称由模型动态形成，应用代码不通过法律关键词表决定案件类型。
规则解释和基于现有描述的是非判断直接给出规则或条件分支，不自动追问；只有区间估计、金额
计算和下一步行动所必需的信息才进入追问审核。没有通过审核的未知要素不会写入案件画像。

这里的“结构化理解”不等于让用户填写表单。系统应先把当前输入和历史上下文整理为
通用核心要素（如法域、当事人、时间线、诉求、证据、争议点）以及领域扩展要素
（如盗窃金额、入户、前科累犯；解除理由、工作年限、月工资；婚前婚后取得时间、登记、
首付与还贷来源等），再用这些要素决定本轮回答和追问策略。

分析过程中用户可以取消当前运行；取消后迟到的模型结果不会写回案件对话。

用户不需要主动“生成案件档案”。案件档案是系统维护案件状态的可检查视图，只有在事实冲突、
识别不确定或用户希望纠正时才需要介入。

## 当前分析契约

分析必须遵守以下规则：

1. 仅把用户提交的案件背景和材料视为本次案件事实来源。
2. 明确区分已证实事实、当事人主张、材料记载和模型推断。
3. 使用 Chunk 级材料编号引用依据，例如 `[M1:C1]`，不得生成不存在的材料引用。
4. 未提供可靠法条或案例来源时，不得虚构名称、条文号、案号或裁判结论。
5. 证据不足或事实冲突时，明确说明不确定性和需要核查的事项。
6. 不给出保证胜诉、精确胜率或替代律师判断的结论。

对话采用 DeerFlow 式动态 Supervisor，不由中间件规定固定顺序。问候、致谢等普通对话直接回答；
普通寒暄和纯抽象规则不需要案件画像；一旦用户描述具体案情、补充案件事实、提出多个争点或继续
既有案件，Case Analyst 必须产出可复用的案件画像。它仍是 Supervisor 体系中的独立专家，不是固定
研究链的一环；法律研究是否需要、查法条还是类案、以及是否并行执行，继续由 Supervisor 按任务和
专家描述动态决定。Case Analyst 的结构化结果由应用层直接形成案件状态和回答合同，不再经过模型
可见的准备工具。
法规与类案原始检索工具仅分配给 Researcher；材料检索和确定性计算仍是主 Agent 的受限直接工具。
每个专家每轮最多尝试一次，检索工具另有硬预算。
没有配置 Embedding Provider 时保持词法检索。事实不足不构成拒绝分析的
理由：Agent 应先基于已知事实和已核验规则给出暂时结论，再提出 Case Analyst 结果中的最多两个高影响
问题。没有检索到已核验法规时，必须明确说明尚无可引用法源，不能把模型记忆表述成已经核验
的法规或类案。法规只能说明法律规则，不能作为案件事实证据。类案只能用于比较事实结构、
争议焦点和裁判思路；系统必须同时说明相似点与差异点，不能因为类案结果推断本案必然得到
相同结果。未经说明样本地区、裁判年份和筛选口径的案例均值或中位数，不得作为刑期、赔偿额
或胜率预测。全国规则授权地区确定具体标准但尚未检索到适用地区规则时，回答必须展示条件
分支，不能用模糊的“通常”替用户选择一个结论。

每轮对话只发起一次流式消息请求。回答按模型消息增量显示；Run 完成后一次性同步持久化状态，
不在生成过程中轮询 Run，也不会因为流事件重复创建用户或助手消息。

检索结果只是候选依据。界面只展示回答正文实际引用的法规和类案，并按首次引用顺序显示为
`[1]`、`[2]`；内部 Chunk 标识只用于持久化追踪，不直接暴露给用户。引用卡片应在当前对话
中展开显示本次实际使用的法条或类案片段，官方来源链接作为核验入口，不把离开当前页面作为
阅读引用内容的默认操作。新引用随消息保存正文快照，旧历史引用没有快照时明确提示。

## v1 推荐方案

当前阶段推荐方案明确为：

~~~text
结构化法律要素层 + RAG
~~~

更具体地说：

~~~text
用户输入
  -> 事项 / 法律问题识别
  -> 核心要素 + 领域扩展要素抽取
  -> 案件档案增量更新
  -> 信息充分度判断
  -> 基于要素检索法规 / 司法解释 / 类案
  -> 先给阶段性分析
  -> 最多追问 1~2 个会改变结论的问题
~~~

当前不把以下两条路线作为 v1 主架构：

- 全量多 Agent 编排：适合后续把合同审查、文书生成、专项合规等能力拆开后再引入；
- archetype / prototype 统计匹配：更适合作为刑事量刑、劳动赔偿等专题增强模块，而不是
  通用法律助手的底座。

## ELLA 可借鉴边界

ELLA 这类系统最值得借鉴的是“把法律依据显式展示给用户”的产品边界，而不是把法条展示本身
当作核心能力。Lexora 可以吸收：

- 回答正文与法规 / 类案依据卡片强绑定；
- 只展示本轮实际引用的依据，而不是所有候选检索结果；
- 允许后续把法规和类案作为可展开、可核查的解释层。

当前阶段不直接照搬：

- 让用户先手动挑法条再生成答案；
- 以法条相似度可视化代替案件理解；
- 把可解释性层放在结构化要素层之前。

Lexora 的主问题仍然是“先把案情理解对”，不是“先展示更多法条”。

## 案件档案

用户可以在案件档案中确认并编辑案件类型、当事人、诉求、关键事实、争议焦点、证据线索和
待补信息。档案会进入后续对话上下文和法规检索查询，但它仍属于用户陈述，不会自动升级为
已经证明的事实。用户在对话中明确陈述或确认信息时，Agent 可以调用案件档案工具增量记录；
模型推断、法律评价和检索内容不得写入档案。档案只在该轮回答成功后与助手消息一起保存，
失败或取消的运行不会留下档案修改。档案是辅助记忆和纠错界面，不是开始分析前必须填写的
步骤。

默认报告结构：

- 案情摘要
- 争议焦点
- 现有材料支持的事实
- 主要论证与反方观点
- 证据评价与矛盾
- 法律适用待核查事项
- 信息与证据缺口
- 建议的后续工作

## 非目标

当前个人版不提供：

- 自动判决或胜诉率预测；
- 无来源的法条、类案或裁判观点生成；
- 律师代理、正式法律意见或诉讼策略保证；
- 登录、多人共享、权限系统和组织级审计；
- 无审核地激活法规版本，或自动判断网页内容是否现行有效；
- 大规模裁判文书或商业法律数据库检索；当前仅接入小规模、已审核的最高法官方类案。

这些能力必须通过后续独立纵向切片引入，不能只靠扩大 Prompt 宣称已经具备。
